# Run11 encryption key usage and compatibility

New encrypted records use envelope v2: `{version:2,salt,nonce,ciphertext}`. Each `sealRecord` call generates a new 256-bit public salt with WebCrypto's CSPRNG, derives a nonextractable AES-256-GCM key from the nonextractable root HKDF key using SHA-256, invokes encryption exactly once, and releases the derived key. HKDF info and GCM authenticated data both contain the canonical tuple `["zigoals-record",2,vault,domain,object,revision,epoch]`. The salt is canonical, unpadded 43-character base64url encoding of exactly 32 bytes. GCM retains a fresh random 96-bit nonce, a 128-bit tag, and the existing 256 KiB plaintext bound. Canonical envelope field order is retained because the sync protocol authenticates ciphertext digests.

Concurrent clients, repeated writes of the same context, retries, backup chunks, and rotated records all receive independent derived keys. Receipt compaction, session counters, restart, or offline state do not reset a cryptographic usage allowance. This is one encryption per derived key, subject to the CSPRNG and HKDF assumptions; random salt collision risk is not claimed to be mathematically zero. A 256-bit salt avoids depending on a global, atomically synchronized nonce counter. New vault root wrapping retains its v1 format: `createVault` generates both a fresh random root and a fresh independent 256-bit recovery secret, then performs one AES-GCM encryption with that wrapping key. Recovery secrets are not reused when a new vault or epoch is created.

Compatibility is forward recovery, not downgrade support. Existing v1 domain-key envelopes remain decryptable, and are never emitted by current `sealRecord`. The Worker continues accepting syntactically valid v1 envelopes so already-persisted pending operations are not silently destroyed; it cannot decrypt or certify client cryptography. Existing ciphertext is not rewritten just by reading it. Ordinary changed records, backup output, and explicit vault rotation use v2. A legacy client does not understand v2 and must upgrade before reading or syncing those records. This change does not retroactively bound encryption already performed by legacy clients, nor claim that an unmodified legacy writer uses the new policy. No deployed data or live migration was changed.

Local evidence: `apps/web/lib/vault/crypto.test.ts` contains a frozen v1 ciphertext fixture, v2 salt/context/tamper rejection, canonical serialization, independent WebCrypto derivation, and repeated-nonce separation across fresh keys. `scripts/run11/envelope-runtime.test.mjs` exercises the real SQLite Worker, malformed input with unchanged stored state, and preservation of old envelopes. Existing backup, rotation-after-restart/lost-ack, selective sync, and cross-account tests run with v2. Initial regressions failed on the former v1-only emitter and v1-only Worker before implementation. This is implementation verification, not a formal cryptographic audit or physical-device/hosted-provider certification.

Primary design references: [RFC 5869 sections 3.1–3.2](https://www.rfc-editor.org/rfc/rfc5869.html) describe salt and context separation in HKDF. [NIST SP 800-38D sections 8–8.3](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-38d.pdf) describe GCM IV uniqueness and invocation constraints under a given key. The per-record derivation is this application's construction using those primitives, not a claim that NIST audited this application.
