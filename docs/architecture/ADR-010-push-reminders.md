# ADR-010: push reminders, a push-only service worker and a separate push Worker

Status: **Accepted and implemented (Session P, PR 4, 2026-10-04); activation is the owner's (docs/run11/PUSH_ACTIVATION.md). Dated addenda below record where the code differs from the first draft.**

## Context
- **In-app reminders exist** ([REMINDERS_V1.md](../product/REMINDERS_V1.md)): a habit and the Water journal can have a reminder time, kept on the device in `zigoals:reminders:v1`; after that time Today shows a card while the app is open. The spec promises "no notifications, no permission prompts and no service worker". People on phones want the same reminder when ZIGoals is closed.
- **ZIGoals installs as a Home Screen app** (Session L): a manifest with `display: standalone`, no service worker, no caching, no CSP change ([STATUS](../STATUS.md), "Installable app").
  - Home Screen web apps keep storage separate from Safari (WWDC23 10120).
  - Since iOS and iPadOS 16.4 they can receive Web Push and show a badge (Safari 16.4 release notes).
  - Safari requires the permission request from a gesture and a visible notification for every push (Apple's web push guide).
  - Desktop Chrome, Edge, Firefox and Safari 16 on macOS support the same standard (MDN compat data).
- **Accounts and the private sync Worker:** email-code sign-in with HttpOnly cookies; the app route forwards the bearer server-side. `workers/private-sync/worker.mjs` verifies it at `AUTH_ORIGIN/auth/v1/user` with the publishable key, checks the `origin` header against `APP_ORIGIN`, requires `x-zigoals-account` to equal the verified user id, reads the session family from the token and keeps a token-hash session registry that revocation and sign-out update (`sessions.mjs`). A Durable Object per account (`PrivateVault`, a SQLite class) holds the data.
- **The six-Worker topology is frozen** by `scripts/run11/activation-check.mjs` (exactly six configs, names, bindings, classes, migrations, compatibility date, no credentials in template vars, no public routes) and documented in [ACTIVATION.md](../run11/ACTIVATION.md).
- **The CSP** is `script-src 'self' 'nonce-…' 'strict-dynamic'` with no `worker-src` (`apps/web/lib/security-policy.ts`), pinned by `lib/public-safety.test.ts`, `tests/public-alpha.spec.ts` and `tests/install-manifest.spec.ts`.
- **The privacy promise:** the server cannot read content ([PRIVACY_NOTICE_DRAFT.md](../legal/PRIVACY_NOTICE_DRAFT.md)). A reminder service must not become the first place where a habit name or a count reaches a server.

## Decision
### Product rules (encoded here)
1. **Private by design.** The server knows only: the account id; each device's push subscription (endpoint and the two browser keys); the send times as `HH:MM`, an IANA zone and weekdays; a quiet-hours window; counters. Never a title, a count, a habit name, a kind or any content.
2. **The notification text is one generic line:** title "ZIGoals", body "A reminder from ZIGoals". The payload carries no text.
3. **Push needs a signed-in account** (the same bearer verification as private sync), which gives delete-on-sign-out and the per-account limits.
4. **Opt-in per device** in Settings → Reminders, with "Turn off and delete from the server". Off by default; on iPhone only in the Home Screen app.
5. **Push when closed, in-app when open, never both.** The person gets one signal per reminder. See "Service worker" for how the platforms constrain the open-app case.
6. **The service worker is push-only:** no `fetch` handler, no caching; registered only after opt-in; unregistered on turn-off.
7. **Limits:** ≤ 5 subscriptions and ≤ 20 schedules per account; ≥ 60 s between sends to a device; ≤ 50 sends per account per day; an endpoint host allowlist; 404 or 410 from a push service deletes the subscription; unsubscribe and sign-out delete the account's data.
8. **Off by default:** the app route answers 503 `PUSH_UNAVAILABLE` while `ZIGOALS_PUSH_ORIGIN` or `ZIGOALS_PUSH_PUBLIC_KEY` is absent. The friends Alpha ships with both absent.
9. **No secrets in the repository:** VAPID keys are generated by the owner locally with `scripts/push/make-vapid-keys.mjs`; tests generate throwaway keys inside the test.

### What the server stores
| Record (per account Durable Object) | Fields | Why | Retention and deletion |
|---|---|---|---|
| Account | the verified user id (the object's name), `created_at` | tenant key | `deleteAll()` on "delete-all", sign-out, account deletion |
| Subscription (≤ 5) | `id`; `endpoint` (https URL, ≤ 2 KB, host on the allowlist); `p256dh` (65 bytes, an uncompressed P-256 point); `auth` (16 bytes); `zone` (the device's IANA zone, for quiet hours); `quiet_from`, `quiet_to` (`HH:MM`); `created_at`, `refreshed_at`, `last_sent_at`; `failures`; `paused` | address and encrypt a message; quiet hours | deleted on unsubscribe, on 404 or 410 from the push service, with the account, and at the next alarm when not refreshed for 30 days (the app refreshes once a day while used) |
| Schedule (≤ 20) | `id`; `subscription_id`; `time` (`HH:MM`); `zone` (IANA); `weekdays` (bit mask, Monday = 1); `next_due` (epoch ms) | when to send | replaced as a set by each `schedule` call; deleted with its subscription |
| Sent marks | `(schedule_id, day)` | idempotent sends | pruned after 2 days |
| Daily counter | `day`, `count` | the 50-a-day cap | pruned after 2 days |
| Not stored | IP addresses, user agents, habit ids, kinds, titles, counts, whether the app is open, logs (`observability.enabled: false`) | | |

### Request flow: subscribe → schedule → alarm → send → cleanup
1. **Subscribe** (client, Settings → Reminders).
   - Preconditions: `'serviceWorker' in navigator && 'PushManager' in window`; a signed-in account; not Showcase; on Apple devices `currentInstallContext() === 'installed'` (a browser tab gets the install hint instead).
   - In the tap's handler: `Notification.requestPermission()`; register `/push-sw.js` (scope `/`, `updateViaCache: 'none'`); `pushManager.subscribe({userVisibleOnly: true, applicationServerKey})` with the key from `GET /api/push`.
   - Then `POST /api/push {action: 'subscribe', subscription: {endpoint, keys: {p256dh, auth}}, zone, quiet: {from, to}, schedules: […]}`.
   - The device remembers its subscription in `zigoals:push:v1`: `{version: 1, subscriptionId, endpointHash, quiet, lastSyncDay}`.
2. **Schedule derivation** (client, pure, `lib/push/schedule.ts`).
   - Each habit reminder becomes `{time, zone: habits.timeZone ?? deviceZone, weekdays}`; `weekdays` follows the habit's schedule (daily and "N per week" → every day; weekday schedules → those days).
   - The water reminder becomes `{time, zone: health.daily.preferences.timezone ?? deviceZone, weekdays: all}`.
   - Rows with the same `time`, `zone` and `weekdays` merge; a row inside the quiet window is refused with a plain message; more than 20 rows keep the 20 earliest times and say so.
   - The set is re-sent (`action: 'schedule'`, an idempotent replace) whenever a reminder time, a habit schedule or a journal zone changes, and once a day on open. A day's `due` state is never sent.
3. **Alarm** (Worker).
   - Each schedule's `next_due` is the next `time` in `zone` on an allowed weekday, converted with `Intl.DateTimeFormat` parts; a time that does not exist on a DST day moves to the next valid minute.
   - One alarm per object at the minimum `next_due`; objects with no schedule delete their alarm.
   - In `alarm()`, in one transaction: select the schedules due in the last 10 minutes without a sent mark for that day; write the marks and the counter; then send one message per subscription (several due rows for one device within 60 s collapse into one send); skip sends inside the subscription's quiet window or above the daily cap; apply the responses; prune; recompute `next_due`; set the next alarm.
4. **Send.** One `POST` to the endpoint with `TTL: 1800`, `Urgency: normal`, `Topic: zigoals-reminder` (a newer message replaces an undelivered one), `Content-Encoding: aes128gcm`, `Authorization: vapid t=<JWT>, k=<public key>`, the encrypted body `{"v":1}` (the service worker reads only its version), a 10 s timeout; only when the endpoint is `https:` and its host is on the allowlist.
5. **Cleanup.**
   - 404 or 410 → delete the subscription and its schedules.
   - 429 → honour `Retry-After` up to one hour; the mark stays (a reminder is never retried later than 10 minutes).
   - 400, 403, 413 or a network failure → `failures + 1`; three in a row → `paused = 1` until the client's next `schedule` call re-sends the subscription.
   - Unsubscribe → delete the subscription and its schedules; if none is left, `deleteAll()` and `deleteAlarm()`.
   - Sign-out, "Revoke other sessions", cloud deletion and account deletion call `action: 'delete-all'` first, with the same bearer.

### VAPID (RFC 8292) and encryption (RFC 8291), in prose
- **Keys.** The owner generates an ECDSA P-256 pair once (`scripts/push/make-vapid-keys.mjs`, WebCrypto `generateKey({name: 'ECDSA', namedCurve: 'P-256'})`). The private key is written as a JWK to an ignored 0600 file for `wrangler secret put VAPID_PRIVATE_KEY`; the public key is printed as the base64url of the uncompressed point (65 bytes starting `0x04`) for `ZIGOALS_PUSH_PUBLIC_KEY`. The ECDH key used for encryption is a fresh pair per message, never the signing key (RFC 8292 §3.2).
- **Token.** Per push-service origin the Worker signs the header `{"typ":"JWT","alg":"ES256"}` and the claims `{aud: <origin of the endpoint>, exp: now + 12 h, sub: VAPID_SUBJECT}` with ECDSA P-256 over SHA-256, serialising the signature as the 64-byte `r || s` that JWS expects. `exp` stays under the 24-hour maximum of RFC 8292 §2. The token is cached for 6 hours per origin, so it is refreshed far less often than Apple's "not more than once per hour" advice.
- **Encryption**, with the subscription's `p256dh` (the user agent's public key) and `auth` (16 bytes):
  - a fresh ECDH P-256 pair; `deriveBits` gives the shared secret;
  - HKDF-SHA-256 with salt = `auth` and info = `"WebPush: info" || 0x00 || ua_public || as_public`, length 32 → the IKM;
  - a random 16-byte salt; HKDF with that salt and info `"Content-Encoding: aes128gcm" || 0x00` → the 16-byte key; info `"Content-Encoding: nonce" || 0x00` → the 12-byte nonce;
  - the plaintext plus the delimiter `0x02`, encrypted with AES-128-GCM and empty additional data;
  - the body is the 86-byte header `salt(16) || rs(4, value 4096) || idlen(1, value 65) || as_public(65)` followed by the ciphertext: one record, under 4 KB (RFC 8291 §4, RFC 8188 §2).
- **Decryption** is the browser's job; ZIGoals never decrypts in production. The tests decrypt with the same primitives.

### The Durable Object (`workers/push-reminders/worker.mjs`, class `PushAccount`)
- One object per account: `env.PUSH_ACCOUNTS.idFromName(user.id)`. The Worker's `fetch` repeats the private-sync preamble in `workers/push-reminders/verify.mjs` (provider check of the bearer, `origin` = `APP_ORIGIN`, `x-zigoals-account` = the verified id, UUID and claim checks), then forwards with `x-verified-account`. The app route additionally confirms, through its existing `/v1/sessions` call to private sync, that the session is still registered and not revoked before it forwards anything.
- Tables, created once in the constructor with `sql.exec`; every request runs in `ctx.storage.transaction`; cursors are consumed synchronously (`toArray()`):

```sql
CREATE TABLE IF NOT EXISTS subscriptions (id TEXT PRIMARY KEY, endpoint TEXT UNIQUE NOT NULL, p256dh TEXT NOT NULL, auth TEXT NOT NULL,
  zone TEXT NOT NULL, quiet_from TEXT NOT NULL, quiet_to TEXT NOT NULL, created_at INTEGER NOT NULL, refreshed_at INTEGER NOT NULL,
  last_sent_at INTEGER, failures INTEGER NOT NULL DEFAULT 0, paused INTEGER NOT NULL DEFAULT 0);
CREATE TABLE IF NOT EXISTS schedules (id TEXT PRIMARY KEY, subscription_id TEXT NOT NULL REFERENCES subscriptions(id) ON DELETE CASCADE,
  time TEXT NOT NULL, zone TEXT NOT NULL, weekdays INTEGER NOT NULL, next_due INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS sent (schedule_id TEXT NOT NULL, day TEXT NOT NULL, PRIMARY KEY (schedule_id, day));
CREATE TABLE IF NOT EXISTS sends (day TEXT PRIMARY KEY, count INTEGER NOT NULL);
```

- `alarm()` is the only sender. Cloudflare runs one instance at a time per object, retries a throwing handler up to 6 times with backoff, and `setAlarm` replaces the previous alarm; the handler therefore catches its own errors and always reschedules. Idempotency comes from the sent marks, written before the outbound call: a crash between the mark and the call loses at most one reminder and never doubles one.
- Routes: `POST /v1/push` with `action` ∈ `subscribe`, `schedule`, `unsubscribe`, `delete-all`; `GET /v1/push` → `{subscriptions: n, schedules: n}`; `GET /v1/push/key` → the public key derived from the private JWK, so the owner can compare it with the app's value. Bodies ≤ 8 KB, exact-key validation like `exact()` in private sync, 60 requests per account per hour (429).
- Validation: `time` matches `^(?:[01]\d|2[0-3]):[0-5]\d$`; `zone` is accepted by `Intl.DateTimeFormat`; `weekdays` is 1–127; `p256dh` decodes to 65 bytes starting `0x04`; `auth` to 16 bytes; the endpoint is `https:`, ≤ 2 KB and on the allowlist.
- Config template `workers/push-reminders/wrangler.local.jsonc`: name `zigoals-push-reminders-local`; `compatibility_date` `2026-09-13`; the `PUSH_ACCOUNTS` binding and migration `v1` (`new_sqlite_classes: ["PushAccount"]`); vars `AUTH_ORIGIN`, `APP_ORIGIN`, `VAPID_SUBJECT` (`mailto:hello@zigoals.app`); `workers_dev: false`; `preview_urls: false`; `observability.enabled: false`. Secrets: `AUTH_PUBLIC_KEY` (publishable, but named like a key) and `VAPID_PRIVATE_KEY`.
- The template is outside `CONFIGS` in `activation-check.mjs`; `--private` and `--source` keep checking exactly the six. A new `--push` validates the push template and its private copy: ignored, 0600, inside the checkout; the same name prefix; exact https origins and no placeholder; no credential-named var; unchanged class, migration and compatibility date; no `LifecycleRecoveryAdmin`; exactly one of a route on the owner's zone or `workers_dev`.

### The app route and the flag
- `apps/web/app/api/push/route.ts`:
  - `GET` answers `{publicKey}`, or 503 `{error: 'PUSH_UNAVAILABLE', message: 'Reminders while ZIGoals is closed are not available in this build.'}`;
  - `POST` reads the session cookie with the same names and rules as `private-account.ts` (a small shared reader with a parity test), requires `x-zigoals-account`, confirms the session through private sync, and forwards the JSON action to `${ZIGOALS_PUSH_ORIGIN}/v1/push` with `authorization: Bearer <token>`, `origin` and `x-zigoals-account`;
  - transport as the sync fetcher: the `PUSH_REMINDERS` service binding when present, otherwise `fetch` to `ZIGOALS_PUSH_ORIGIN`.
- Values: `ZIGOALS_PUSH_ORIGIN` (an exact https origin) and `ZIGOALS_PUSH_PUBLIC_KEY`. Both are supplied with `wrangler secret put` on the app Worker's private config, like `ZIGOALS_AUTH_PUBLIC_KEY` (the checker refuses key-named vars in templates), so no generated app config changes and no activation tooling beyond `--push`.
- The owner may later move to the service binding and a nonpublic push Worker; that needs an additive `make-private-configs.mjs --set-push-binding` and is listed as an owner decision.

### Service worker (`apps/web/public/push-sw.js`)
- Handlers: `install` → `skipWaiting()`; `activate` → `clients.claim()`; `push`; `notificationclick` → close the notification, then focus a window client of the origin or `openWindow('/app')`.
- No `fetch` handler, no `caches`, no IndexedDB, no `importScripts`; a plain script file, pinned by a test that greps it.
- **`push`:** `clients.matchAll({type: 'window', includeUncontrolled: true})`; if a client is `visible`, post `{type: 'zigoals:push-reminder'}` to it so Today refreshes its reminder cards at once; show the notification `('ZIGoals', {body: 'A reminder from ZIGoals', tag: 'zigoals-reminder', icon: '/icons/zigoals-192.png', data: {url: '/app'}})`.
- **The open-app case, decided by the platforms** (sources below, read 2026-10-03):
  - Apple: "Safari doesn't support invisible push notifications. Present push notifications to the user immediately after your service worker receives them. If you don't, Safari revokes the push notification permission for your site."
  - Microsoft: if no notification is shown, "Microsoft Edge displays a generic notification"; `userVisibleOnly` must be `true`, and Chrome and Edge reject `subscribe` otherwise (MDN).
  - So the literal mechanism "post a message instead of showing a notification" would cost the permission on iPhone and show a stranger's text on Edge; it is **not** implemented.
  - Rule 5 is kept as follows: closed app → the notification only; open app → the platform shows the notification and the app shows its usual in-app card for that reminder, never a second card or a second notification; the `tag` collapses repeats.
  - Telling the server to skip a send while the app is open would reveal when the app is used and is rejected on privacy grounds.
  - **Owner decision requested:** accept this reading of rule 5.
- `pushsubscriptionchange`: nothing in the worker. On the next open the app compares `pushManager.getSubscription()` with its stored endpoint hash and re-subscribes.
- **CSP:** `worker-src 'self'` is added. Under `'strict-dynamic'` the `'self'` source of `script-src` is ignored, and a worker URL carries no nonce, so without its own directive the registration would be refused. The three pins are updated in the same commit [Tier 3 (CSP)].

### Error handling
| Where | Case | Behaviour |
|---|---|---|
| Client | permission denied | the panel says it is blocked in the device settings; nothing is sent |
| Client | `subscribe` rejected (`NotAllowedError`, `NotSupportedError`) | plain message; the worker is unregistered again |
| Client | 503 `PUSH_UNAVAILABLE` | the panel shows "Not available in this build"; the offer line is hidden |
| Client | 401 or 409 from the route | the usual sign-in or account-changed handling; the device key is cleared |
| Client | storage refuses the device key | the subscription is deleted again on the server; the person is told |
| Worker | invalid body, endpoint or keys | 400 with a code (`INVALID_PUSH_REQUEST`, `ENDPOINT_NOT_ALLOWED`); nothing stored |
| Worker | limits | 409 `SUBSCRIPTION_LIMIT` or `SCHEDULE_LIMIT`; 429 on the hourly request cap |
| Worker | push service 404 or 410 | the subscription is deleted; the device re-subscribes on its next open |
| Worker | push service 429, 5xx, timeout | failure counted, paused after three; the reminder is not retried |
| Worker | an alarm fires late | due rows older than 10 minutes are marked and skipped, never sent stale |

## Alternatives considered
- **A third-party push SaaS.** Rejected: it would see every endpoint and every send, usually wants an SDK (a dependency) and a tracker, and adds a processor for no gain; the standard protocol needs only `fetch` and WebCrypto.
- **A cron Worker without Durable Objects.** Rejected: a cron would need a central store of every account's schedules and would scan it every minute; per-account objects wake only when due, keep each account's data isolated, and give transactions and alarms for free.
- **Content in the payload** (the habit's name, the count). Rejected: it breaks rule 1 and the privacy promise; the browser would decrypt it, but the server would have to know it to send it.
- **No push at all.** Rejected by the owner: the in-app reminder cannot reach a closed app, and the Home Screen app would stay silent.

## Consequences
- **Privacy.**
  - Our server learns the schedule metadata in the table above and nothing else.
  - The device's push service (Apple, Google, Mozilla or Microsoft, depending on the browser) learns that a message for this device arrived at these times, with an encrypted body.
  - Someone who obtains an endpoint cannot push to it without the VAPID private key: the subscription is bound to the public key.
  - PRIVACY.md, the privacy notice and the legal checklist say so in the same words.
- **Cost (order of magnitude, COST_MODEL assumptions A1–A4).**
  - 20 friends × 2 reminders a day ≈ 40 sends; each alarm is one Durable Object request and a handful of rows; schedule refreshes add ≈ 20 requests a day: about 100–200 requests and under 1,000 rows written a day, under 1% of the Free figures read today (100,000 requests and 100,000 rows written a day). At 1,000 people it is 5–10% of those figures.
  - Sends are Worker subrequests, not Durable Object requests. The push services' documentation read today lists no price for delivery; no claim beyond that is made. No paid service is added.
- **Legal (for the lawyer, LEGAL_CHECKLIST §2.6).**
  - The subscription and the worker are stored on the device only after an explicit request, and the server-side schedule exists only for a feature the person turned on; whether the ePrivacy Art. 5(3) exemption for a service "explicitly requested" applies, or consent must be recorded, is the lawyer's call.
  - The notice must state: what the server stores (the table); that the platform's push service delivers the message and sees its timing; the fixed text; retention (30 days without refresh; deletion on turn-off, sign-out and account deletion); how to turn it off.
  - Health reminders carry no health content, but a water reminder's existence is a fact about the person; the Health consent wording should mention it.
- **Operations.** The owner activates push with `docs/run11/PUSH_ACTIVATION.md`:
  1. generate the keys locally;
  2. copy the template to the ignored 0600 private copy; set the origins and the route;
  3. `node scripts/run11/activation-check.mjs --push`;
  4. after the Stage 7 style approval, `wrangler secret put AUTH_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` on the push Worker, then deploy it;
  5. `secret put ZIGOALS_PUSH_ORIGIN` and `ZIGOALS_PUSH_PUBLIC_KEY` on the app; compare `GET /api/push` with `GET /v1/push/key`;
  6. run the Stage 8 push row: the iPhone Home Screen app receives one reminder with the app closed.
- **What stays off:** the Alpha deploy of this PR activates nothing; every build answers 503 and shows only the panel's "Not available in this build"; the six Workers and their checks are unchanged; no badge is set (the Badging API is noted for a later decision).

- **Human-only:** a real iPhone Home Screen app receiving a reminder with the app closed, Safari's permission behaviour, and the real push services (the Stage 8 row).

## Rollback
- **App:** revert the PR and redeploy through the Manual Alpha workflow; an older build has no route, so the panel and the offer disappear. A worker registered by the newer build stays registered until the person clears site data; it has no `fetch` handler, so it changes nothing in the old build. The owner can delete the push Worker's secrets and the Worker; its objects go with it.
- **Worker alone:** delete it or leave it undeployed; the route answers 503 and the panel says so.
- **Flag:** removing the two app values turns everything off without a deploy; subscriptions on the server stay until the owner deletes the Worker.

## Addendum (2026-10-04, implementation)
- **Hosts.** All four push services are now verified on first-party pages (read 2026-10-04) and built into `workers/push-reminders/hosts.mjs`: `*.push.apple.com` (Apple), `fcm.googleapis.com` (Google, the Chromium source `components/push_messaging/push_messaging_constants.cc`; non-Stable Chrome uses `jmt17.google.com`, not built in), `*.notify.windows.com` (Microsoft: the Edge policy `ForceBuiltInPushMessagingClient` and the WNS overview, "the channel URI uses the domain notify.windows.com"), `updates.push.services.mozilla.com` (Mozilla autopush). The optional var `PUSH_ALLOWED_HOSTS` (comma-separated exact hosts or `*.suffix`) adds hosts without a code change; `--push` validates it.
- **Sign-out unsubscribes this device only.** Deleting the whole account's push data at sign-out would silence the person's other devices, so sign-out sends `unsubscribe` for this device's subscription; "Revoke other sessions", cloud deletion and account deletion send `delete-all` (after a revoke, this device subscribes again at once). Devices without a push record make no request.
- **A replaced subscription.** Turning push on always replaces a browser subscription left by an earlier account or key on the same browser: its old address then answers 404 or 410 and the other account's server data leaves by itself.
- **Test files** live where the root Vitest config finds them: `scripts/run11/push-webpush.test.mjs` (RFC 8291 Appendix A and RFC 8292 §2.4), `scripts/run11/push-clock.test.mjs`, `scripts/run11/push-runtime.test.mjs` (Miniflare), `scripts/run11/activation-check-push.test.mjs`, `scripts/push/make-vapid-keys.test.mjs`; the app's tests under `apps/web/lib/push/`, `apps/web/lib/server/push-route.test.ts`, `apps/web/lib/server/session-cookie.test.ts`, `apps/web/tests/push-reminders.spec.ts`.
- **Fixture clock.** The Worker accepts a test-only action (`fixture`: a fixed clock and an immediate alarm run) only when the var `ISOLATED_FIXTURE` is `"true"`; `--push` refuses that var in the template and in the private copy.
- **The app route** reads the session cookie through `apps/web/lib/server/session-cookie.ts`; the account route keeps its own inline reader, and `session-cookie.test.ts` proves both read the same token from the same request. The route needs `ZIGOALS_SYNC_ORIGIN` as well (the session check), so without accounts configured it answers 503 like everything else.
- **The device key** `zigoals:push:v1` lives in the account's own storage (through `getAppStorage()`), so a locked account shows "Unlock your account records first." and the schedule refresh runs only while the records are unlocked; the server deletes a subscription not refreshed for 30 days.
