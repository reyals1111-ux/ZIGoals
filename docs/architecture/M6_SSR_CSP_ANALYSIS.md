The ~6.84% bundle reduction remains supported. The analysis below retains its original local measurements and source scope; it does not attribute the production spikes.

Implementation decision: retain Next16.3.5/OpenNext1.20.6 and fresh response nonces. Move only the known public icon and crawler policy out of Next metadata handlers. No dependency upgrade, framework migration or signing change. Implementation performed no production action; the subsequent owner rollout is recorded separately above.

1. **Which routes require SSR today?** Root `app/layout.tsx` calls `connection()` and reads middleware origin for metadata. `/`, `/app`, its goals/settings/ecosystem screens and HTML404s use request-time rendering. No goal balance, wallet identity or private metadata needs server lookup; their state loads in the browser.
2. **Which are dynamic because of CSP?** All HTML shares that layout. The primary request-time need is the nonce; canonical/OpenGraph origin is also request-derived. Static content/local-demo initial shells otherwise do not need personalized SSR. `/icon.svg`, `/robots.txt`, social cards and built CSS/JS/fonts do not need a nonce.
3. **What is server-generated?** Fresh CSP nonce, initial HTML/React stream, request-origin canonical/social metadata and security headers. Build identity is computed at build time. Goal data stays in browser storage; testnet diagnostics and explicit wallet connection are browser actions.
4. **Could it be mostly static/client-rendered?** The product's data model permits it in principle. Existing React Client Components still have an initial server render. A static shell would need deliberate navigation,404,metadata,hydration and script-policy design, not simply removal of `connection()`.
5. **What would nonce removal lose?** The current policy authorizes the scripts of each individual response with an unpredictable nonce and `strict-dynamic`; untrusted injected inline scripts lack it. A fixed/reused nonce destroys that property. Removing nonce rendering alone would break hydration or require weakening the policy.
6. **Are hashes/SRI viable with current Turbopack?** Potential future work, not a validated replacement. The installed16.3.5 Turbopack build reads `experimental.sri.algorithm` and passes `sriEnabled` to its manifest loader. Current installed/online CSP guidance describes experimental SRI without the older webpack-only limitation. Do not assert Turbopack universally lacks SRI. External bundle integrity does not by itself authorize or protect inline React/bootstrap payloads. Exact hashes, dynamic route payloads, streaming, CSP enforcement and the OpenNext output must all be proven together before adopting it. No SRI build experiment was needed for this bounded fix.
7. **Must a static shell weaken CSP?** Not inherently: a designed hash policy or externalized bootstrap could be strict. This repository has no demonstrated equivalent design. Adding `unsafe-inline`, production `unsafe-eval`, broad origins or static/reused nonces is rejected.
8. **Middleware or SSR dominant?** Not resolved quantitatively. Baseline metadata icon and robots unnecessarily pass middleware/Next dispatch. First local `/app` wall261.595ms versus later10.934–18.831ms suggests initialization work, but includes workerd/client overhead. Startup profile sampled19.018ms active with only16 samples and did not call the application fetch handler. Those unlike measurements cannot assign a percentage to middleware, React, JIT or parsing. Next/React/lazy route initialization is plausible; owner539/285ms spikes remain unattributed.
9. **Static-shell migration cost/risk?** Separate milestone: prove inline-script handling and equivalent security with injection tests; private deep links/canonical metadata; hydration/reload/local storage/reconnect; image and404 behavior; deployment/cache invalidation; matched production CPU. Avoid a custom HTML rewriting/cache design merely to save a few milliseconds.
10. **What could vinext change?** Cloudflare now recommends its Vite-based Next API implementation and labels it beta. A different bundling/runtime path might alter startup/SSR overhead, but does not remove nonce request-time needs. Compatibility, wallet hydration, metadata, CSP propagation and measured CPU in this app are unknown. OpenNext remains a documented existing-app path. No installation, compatibility run or migration in M6.

## Import and generated-bundle audit

The baseline OpenNext entry loads image/context/skew/middleware support globally, then dynamically imports the default Next server handler on requests that need it. Wrangler's startup tool profiles entry import only; application lazy initialization falls outside that profile. No actual Cloudflare deployment `startup_time_ms` was obtained during the original local analysis, when upload was outside its scope.

Baseline dry-run is9382.72KiB (gzip1759.83KiB),393 server metafile inputs. Source-map inventory in [LOCAL_BASELINE_ANALYSIS](../verification/m6/LOCAL_BASELINE_ANALYSIS.json) detects CosmJS, generated protobuf, Zod, Decimal, registry, goal-engine and shared schemas. Original source bytes include precompiled and lazy modules; they are neither emitted contribution nor executed CPU. Next/React runtime chunks are also substantial. No clear new eager signing import was found: wallet signing/query clients already use dynamic imports; financial refusal precedes signer work. Zod/Decimal/registry support existing rendering/validation. No source attribution in the16-sample startup profile justifies moving these boundaries or duplicating schemas/business rules. Static file routing is the supported low-risk improvement; larger import surgery is deferred.

## Routing and guardrail

Cloudflare serves matching public assets before the Worker. Baseline icon and robots were absent from that package and returned nonce/no-store through Next; public placement removes their application invocation path. Explicit icon metadata preserves its URL/type; robots bytes remain identical. Tight matcher boundaries prevent prefix/lookalike404 HTML from losing CSP; the nonexistent `/favicon.ico` now retains the HTML security path. `/_next/image` stays an exact image-handler endpoint, not a general bypass. All static assets get frame denial/nosniff/referrer/permissions/HSTS/noindex via `_headers`; hashed build assets retain immutable caching. HTML retains nonce and no-store.

Alpha `limits.cpu_ms=2000` was selected at about3.71 times the baseline owner-observed539ms spike and15 times below the documented Paid30,000ms default. It is now present in deployed config but **not separately confirmed by dashboard/version view**. It limits invocation CPU, not network waiting or total monthly cost. Cloudflare permits occasional over-limit flexibility; consistent excess can terminate execution (1102/`exceededCpu`). The owner's exact-version last-1h window recorded zero such events. This small sample cannot guarantee the cap accommodates every legitimate request or independently prove enforcement. No new storage or paid product was added. Duplicate HSTS and X-Robots-Tag values on dynamic `/app` are a minor cleanup candidate, not a rollback issue.
