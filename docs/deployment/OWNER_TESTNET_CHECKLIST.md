# Owner testnet deployment and exit checklist

**Financial contract prepared, not deployed.** The public web Alpha is live; that does not enable this checklist’s financial operations. Use only `zig-test-2`; never mainnet or real funds. Stop on any mismatch. Funding and upload permission remain external prerequisites. No faucet request or transaction is automated by this checklist.

1. **Public developer address.** Select the dedicated Keplr test account; compare its full public `zig…` address in wallet/app/support approval. Never copy a seed or key.
2. **Test balance.** Read the official REST bank balance; denom must be `azig`, display precision18. Reserve estimated fees separately from the tiny smoke deposit. Zero balance means stop.
3. **Upload permission.** Obtain support confirmation for this exact address and verify current `wasm params` with the official CLI/query method. An unavailable query, HTTP501 or an unconfirmed allowlist means stop; do not probe by repeatedly uploading.
4. **Reviewed canonical artifact.** Obtain the exact downloaded candidate from successful manual main-branch release issuance. Verify the independently reviewed full source commit, both clean build jobs, actual bytes/size/hash, source tree/lock/environment and trusted validator using [VERIFY_RELEASE_ARTIFACT.md](VERIFY_RELEASE_ARTIFACT.md). Require both Wasm and manifest attestations from the expected main source/signer workflow. Preserve the full candidate manifest and run URL. Local `artifacts/` output, compatibility builds, single builds and unsigned PR inspection drafts do not authorize upload. Obtain separate explicit owner approval of that exact attested checksum; never substitute rebuilt bytes.
5. **Upload.** Owner reviews/simulates and signs a testnet store-code transaction from that account. Record its locally computed/returned hash immediately. On timeout, check the existing hash; never blindly repeat.
6. **Code ID.** Wait for successful included receipt. Extract code ID from the correct store-code event; query code info and verify the onchain checksum equals the reviewed SHA256. Receipt success alone is insufficient.
7. **Immutable instantiate.** Owner signs instantiate for that code ID with `{"admin":null,"native_denom":"azig"}`, no funds, label `ZIGoals Goal Manager testnet`, and **no chain-level migration admin** (`--no-admin` in the official CLI). The JSON `admin` is optional deposit-pause authority, distinct from chain migration admin. Default both to none.
8. **Contract metadata.** Verify included instantiate receipt and contract address, code ID, empty chain admin, cw2 name `crates.io:zigoals-goal-manager`, version `0.1.0`, configured `azig`, null pause admin, deposits unpaused, zero initial recorded liabilities. Check live node chain/version/denom again.
9. **Contract explorer evidence.** Open the exact testnet contract page in the validated ZIGScan explorer and confirm it resolves to the instantiated contract and code ID. Record the actual verification time and URL; do not call a homepage or missing detail URL proof.
10. **DEPLOYED manifest gate.** Assemble and structurally validate the strict [v2 public manifest](MANIFEST_V2.md), including upload, instantiate and explorer evidence. Confirm its status is `DEPLOYED`, with exact code ID/address/checksum, immutable null migration admin, approved pause admin, and live chain/version/denom/cw2 reads. Do not add smoke receipts as strict manifest fields.
11. **Configure frontend.** Place the reviewed DEPLOYED v2 manifest in `apps/web/config/deployment.json`, explicitly rebuild with `NEXT_PUBLIC_APP_ENVIRONMENT=TESTNET_DEPLOYED`, and reopen. A manifest alone cannot enable actions. Legacy address/code-ID environment variables no longer enable financial actions. Guarded client must accept the actual reviewed contract; do not weaken identity checks if it refuses.
12. **Tiny Goal.** Create a Goal without funds. Verify correct owner and actual event-derived Goal ID. Name/target/date/private notes must not appear in the wallet execute message or chain event. Creation is not a deposit.
13. **Tiny deposit.** Example test amount: `1000000000000000azig` (0.001 test ZIG), if balance covers this plus simulated fees. Exactly one `azig` coin; record before/after bank balance, Goal position, liabilities and tx hash.
14. **Partial withdrawal.** Withdraw `400000000000000azig` (0.0004 test ZIG). Recipient is stored owner. Check Goal position is `600000000000000`; wallet delta includes network fee.
15. **Complete withdrawal.** Withdraw the exact remaining position. Check position and this Goal's liability contribution are zero; never send an extra deposit to recover funds.
16. **Close.** Close the empty Goal. Closed history remains queryable and further deposit/withdraw rejects. If pause admin was deliberately configured in a separate reviewed deployment, separately prove pausing deposits still permits exit.
17. **Smoke receipts.** For each smoke receipt verify code0, hash, height, matching sender/contract/execute message/funds, and events from this contract. Keep these hashes, heights and timestamps in separate smoke evidence; unknown or malformed receipt remains uncertain. Keep private plans offchain.
18. **Balances.** Reconcile bank deltas including actual fees, Goal positions and contract liabilities. Contract balance must cover total liabilities. Any unexpected direct-transfer surplus must be explained; it is not withdrawable user credit.
19. **Deployment record.** Preserve the reviewed v2 manifest with code ID/address, public deployer, artifact checksum, upload/instantiate receipt hashes, explorer URL/verification time, source commit, chain/version/denom, instantiate JSON and both admin fields. Back up private Goal metadata and the separate smoke evidence.

Abort on mismatched chain/denom/address/checksum/code/admin, stale account, unexpected permission/message/funds/fee, inability to verify upload permission, receipt uncertainty or accounting mismatch. Do not retry ambiguous broadcasts. For a deployed defect, pause new deposits only if that authority exists, preserve user withdrawals, disable the frontend configuration and investigate. An immutable contract cannot be rolled back or patched in place; replacement requires a new reviewed deployment. Existing funds never move automatically to a replacement.
