# M4 frontend engineering security / privacy review — merged M3 baseline
Scope: reviewed actual source in ZIGoals at HEAD `9816627438cfed9d3b2f8691a683b0c334b56f7c` (M4 documentation-only commit over merged M3 frontend); read-only except this report and isolated predicate reproduction. This is an engineering review, not a professional audit.
**Outcome: no material custody/security bypass established; one LOW defensive-validation finding.** New public deployment-mode/CSP work remains a separate release gate and is not covered as implemented here.
**F1 — LOW, malformed RPC Goal responses can break financial views.** `apps/web/lib/wallet.ts:116`–128 accepts Goal objects after only owner/denom comparisons and a coercing digits regex on `position_units`; it does not validate remaining generated Goal fields or enforce requested page size. A response with `position_units: "1".repeat(101)`, `id: "../settings"`, `status: "unexpected"` passes. `apps/web/components/goal-card.tsx:18` calls valuation outside its recovery try, and `packages/chain-config/src/index.ts:71` rejects the oversized amount in `formatUnits`, breaking rendering. Numbers such as 9007199254740992 also pass the regex, defeating canonical integer-string validation. This requires malformed/compromised trusted RPC data; no unauthorized transfer or secret disclosure was demonstrated.
F1 evidence/fix: isolated Node execution of the exact readGoals owner/denom/regex predicate printed `number: accepted=true, goal_id=../settings, status=unexpected` and `oversized-string: accepted=true, goal_id=../settings, status=unexpected`. Add bounded strict runtime parsing compatible with generated Goal schema before returning data: canonical Uint64 IDs/timestamps, Uint128 integer strings, expected owner/denom/idle strategy, valid status and bounded nullable commitment; reject pages over 100 and duplicate/nonprogressing IDs. Targeted regression should prove malformed rows never reach rendering; preserve ordinary contract-generated responses. Reproduction exercised the acceptance predicate only, not a browser crash or live endpoint.
Transaction/Keplr review: `wallet.ts:57` guards each connection await; `wallet.ts:230`–319 builds journal intent from the exact execute message, reacquires signer, checks revision/expiration/current key/signer account/chain before and after signing, reruns immutable deployment evidence before signing, and verifies signed sender/contract/message/funds before broadcasting. Keplr remains trusted for account permission/key custody and its fee approval UI; signed fee/auth bytes are not independently compared against the quote by `verifySignedOperation` (`receipt-reconciliation.ts:103`). No broadened permission or automatic wallet signing path found.
Manifest/evidence/network: `packages/shared-types/src/deployment.ts:45`–149 strictly binds v2 testnet/address/code/provenance fields and clean deployed state; `contract-evidence.ts:8`–38 checks code ID, no migration admin, creator, checksum, native denom, pause admin and cw2 identity. `packages/chain-config/src/index.ts:18` pins canonical testnet endpoints/denom/decimals. Runtime chain/evidence observations trust the configured RPC/REST; they are not consensus proofs or independent artifact provenance. This documented trust is not a new finding.
Receipt/storage/multitab: `transaction.ts:48`–67 saves a signed hash durably before broadcast; `receipt-reconciliation.ts:42`–101 rehashes bounded receipt bytes and matches operation identity before accepting code/height, retaining null/timeout/mismatch as uncertain. `transaction-journal.ts:186`–296 uses serialized strict-durability writes, monotonic terminal states and atomic cross-record hash ownership. Provider `goal-provider.tsx:523`–552 rechecks scoped durable revision under Web Locks; metadata uses the same cooperative-lock/revision principle (`storage.ts:25`, `storage.ts:113`). Unsupported/corrupt rows are preserved with warnings. First-terminal RPC trust, old/nonparticipating tabs, other origins/devices, clock changes, eviction and abrupt shutdown remain documented limits; uncertain operations are never automatically replayed.
Metadata/import/XSS/links: `packages/shared-types/src/index.ts:36`–103 uses bounded strict schema, numeric raw goal keys, 1 MB UTF-8 limits, 1000-goal ceiling and matching wallet/chain; `storage.ts:46`–81 validates merged output and preserves damaged bytes before replacement. Reviewed render sites use React text escaping, with no HTML/eval sinks. Explorer routes are compiled/validated and open with `noopener noreferrer` (`components/explorer-links.tsx:17`–27); provider/reference URLs are HTTPS validated. Backups are browser Blob downloads (`app/app/settings/page.tsx:13`–24), not uploads. No new exploitable injection path established.
Privacy source trace: Goal name/target/date/notes/preferences flow only to local metadata/planning/render/export/import. `goal-provider.tsx:428`–438 builds create/deposit/withdraw/close messages without plan fields; wallet simulation/signing uses only public execute intent and an empty memo. No analytics, beacon, remote font, sync/upload, or private-plan external request path was found in the reviewed app. No stronger claim is made about extensions, compromised same-origin code, browser backup/sync, screenshots or exported JSON.
Actual external disclosures: wallet connection exposes selected public address to the app; RPC/REST receive public account/contract/query goal IDs, actual intended transaction amounts (including simulation), signed transaction/hash and normal transport identifiers/IP. Explorer clicks send the selected public identifier; provider/Hub links navigate to external services. Hosting sees requested app routes, including `/app/goals/<public-or-local-goal-id>`, and normal request metadata. Local goal IDs can therefore appear in hosting route/access logs even though private names/targets/dates/notes do not. Diagnostics contact public endpoints explicitly, including from local simulation. These exceptions should appear in final M4 privacy documentation.
Existing release requirements, not newly discovered material defects: `apps/web/next.config.ts:53`–55 permits production `script-src 'unsafe-inline'`; provider `goal-provider.tsx:799`–804 currently gates only by local health or connected wallet+deployed address, with no independently asserted build deployment mode. The assigned M4 worker must complete nonce production CSP and mode enforcement at preparation/signing/broadcast boundaries; review final code and runtime headers afterward.
Coverage/limits: inspected source and named existing wallet, journal, receipt, storage and multitab regression cases; did not rerun the coordinator's baseline, use a wallet/broadcast, install dependencies, edit source, or claim a deployed/public-host result.
