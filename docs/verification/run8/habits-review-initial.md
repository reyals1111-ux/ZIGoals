# Habits Beta correctness review

- **P1 — Completion-count endings count check-in rows, not completed target periods** (`apps/web/lib/habits.ts:138-145`). `successfulEntriesBefore` applies the per-entry target to every row. A 3×/week habit with `endCondition: { completions: 1 }` stops scheduling after the first successful day, before the week can complete; conversely a weekly 60-minute habit logged as 20+40 completes the week but never advances the completion end condition. End counts must consume the same day/period outcomes as `habitStats`.
- **P1 — Pausing or editing an aggregate habit mid-period retroactively creates a failure** (`apps/web/lib/habits.ts:155-167, 215-231`). `segmentBounds` truncates the old week/month/year at the day before the new rule, then `periodResult` treats that truncated segment as closed and failed. Pausing a weekly habit on Tuesday therefore records Monday’s partial week as a failure and breaks its streak; resuming in the same week creates a second target period. This violates prospective-change and pause-does-not-penalize semantics.
- **P1 — The editor accepts frequency goals the storage model can never satisfy** (`apps/web/lib/habits.ts:17, 53-55, 161-165`; `apps/web/components/habits/habit-editor.tsx:95`). A period can hold only one entry per calendar date, and frequency completion counts successful entry rows, yet `times` allows up to 366 for every period. For example, 8×/week is valid input but can reach at most seven successes, leaving the habit permanently failed/incomplete.
- **P2 — Streaks combine incompatible cadence units and relabel history using the current rule** (`apps/web/lib/habits.ts:214-236`; codified by `apps/web/lib/habits-beta.test.ts:151-166`). Outcomes from weekly/monthly and daily rules are appended to one counter without a cadence boundary, while `streakUnit` comes only from the latest rule. A completed week followed by one daily completion is shown as a “2 days” streak, although one member is a week.
- **P2 — Goal-target end conditions are exposed as working but never affect scheduling** (`apps/web/lib/habits.ts:141-145`; `apps/web/components/habits/habit-editor.tsx:99-101`). `endAllows` returns `true` unconditionally for `kind: "goal"`; the UI offers “Until linked Goal reaches target” without saying that this end condition is data-only, so a habit continues forever after its Goal completes.
- **P2 — Frequency targets are displayed with the wrong period** (`apps/web/components/habits/habit-card.tsx:12-16`; `apps/web/components/habits/habit-editor.tsx:72, 89`). Frequency inputs are forced to `targetPeriod: "day"` even though evaluation uses `schedule.period`, so a monthly “Buy ZIG” target is evaluated monthly but rendered as “500 USD per day.”
- Verification: `pnpm exec vitest run apps/web/lib/habits.test.ts apps/web/lib/habits-beta.test.ts` passed 24/24; the defects above are uncovered semantic paths, not current-suite failures.
