# Barcode decoder selection and limits

The Health scanner uses a browser-native `BarcodeDetector` only when it supports all three required formats: EAN-8, EAN-13 and UPC-A. Missing, partial or failed native format probes select a dynamically imported, exact-pinned local `@zxing/browser` 0.2.1 (MIT) and `@zxing/library` 0.23.0 (Apache-2.0) after an explicit Scan action. The fallback limits the reader to those same three product-label formats. It requires a rear-camera stream and keeps frames on device; no CDN script, camera frame upload, microphone request or automatic food lookup is involved. Both paths require two adjacent valid readings; an unreadable frame resets confirmation. A code stays in the editable input until the person separately chooses lookup and reviews any product before logging it.

Package/source review: [browser package and license](https://github.com/zxing-js/browser/blob/master/package.json), [browser camera API](https://github.com/zxing-js/browser/blob/master/README.md), [library source and license](https://github.com/zxing-js/library). The exact installed copies and integrity hashes are in `pnpm-lock.yaml`. Browser package dependency metadata and installed license files were checked locally. No subscription or remote decoder service was added.

Local Playwright evidence includes native detector fixtures, absent/partial/throwing format probes, unavailable or constrained rear camera, panel close/navigation/account-change cleanup, stale-scan and video-attachment fences, manual leading-zero lookup, and actual fallback decoding of a synthetic leading-zero EAN-8 label without a lookup request. The focused desktop/mobile suite passed 28/28 serially; a confirmation unit checks that blank/invalid frames break adjacency. These are local synthetic camera tests, not physical Safari/Chrome phone acceptance. A safe HTTPS origin, real phone camera gesture and provider lookup activation remain separate gates.
