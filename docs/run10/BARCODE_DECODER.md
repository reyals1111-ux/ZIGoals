# Barcode decoder selection and limits

The Health scanner first uses a browser-native `BarcodeDetector` when it supports EAN-8, EAN-13 or UPC-A. Otherwise an explicit Scan action dynamically imports exact-pinned `@zxing/browser` 0.2.1 (MIT) and `@zxing/library` 0.23.0 (Apache-2.0) from the application bundle. The fallback limits the reader to those same three product-label formats. It reads the rear-camera stream locally; no CDN script, camera frame upload, microphone request or automatic food lookup is involved. The native and fallback paths both require two consecutive valid readings. A code stays in the editable input until the person separately chooses lookup and reviews any product before logging it.

Package/source review: [browser package and license](https://github.com/zxing-js/browser/blob/master/package.json), [browser camera API](https://github.com/zxing-js/browser/blob/master/README.md), [library source and license](https://github.com/zxing-js/library). The exact installed copies and integrity hashes are in `pnpm-lock.yaml`. Browser package dependency metadata and installed license files were checked locally. No subscription or remote decoder service was added.

Local Playwright evidence includes native detector fixtures, permission denial, unavailable camera API, panel close/navigation/account-change cleanup, manual leading-zero lookup, a synthetic camera stream using the fallback, and an actual fallback decode of a synthetic leading-zero EAN-8 label with no lookup request. These are local synthetic camera tests, not physical Safari/Chrome phone acceptance. A safe HTTPS origin, real phone camera gesture and provider lookup activation remain separate gates.
