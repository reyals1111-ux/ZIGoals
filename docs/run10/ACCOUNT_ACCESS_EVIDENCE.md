# Account access and isolation checkpoint

- Implemented email-code access UI, 60-second resend cooldown, server-verified account status, honest configuration-unavailable state, and sign-out with a client key-cleanup callback. No hosted email was sent or real account used.
- Verify/status return only a validated provider UUID; access tokens stay in the HttpOnly cookie. Status uses the auth identity endpoint, separate from vault reads. Sign-out clears the cookie even when hosted configuration disappears or provider revocation fails.
- Vault GET and sync POST require a captured `X-Zigoals-Account` UUID and forward it alongside cookie-derived credentials. The worker must compare that fence with authenticated identity; the header never chooses server ownership.
- Account-session contract: getAccountScope/getAccountGeneration/isAccountLocked, activateAccount/lockAccount/clearAccountSession/unlockAccount, and ACCOUNT_CHANGE. A persisted selector is never authentication proof; cold reload and activation start locked. Root vault integration owns identity recheck and actual key unlock.
- Account records use `zigoals:account:v1:<uuid>:` local namespaces. Old Storage objects are revoked on lock, switch and same-account reactivation; failed selector removal still revokes access. Existing local records are not copied. Showcase remains isolated and can be viewed while the account stays locked.
- Profile-wide BroadcastChannel messages contain only `lock`; sign-in/switch/sign-out broadcast, unlock never broadcasts, received messages can only lock. Unsupported channels leave server account fences active but do not provide immediate cross-tab key invalidation.
- GoalProvider clears private views, review state and wallet context on account changes. Operation revisions reject queued simulation edits, account generations reject delayed plan writes/outcomes, and late wallet reads cannot repopulate a different account. Cross-tab storage keys include the account namespace.
