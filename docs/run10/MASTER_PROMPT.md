## 10. Client encryption, key custody and recovery

**ENC-01 — Write the threat model before cryptographic code.** Define what server operators, auth providers, storage providers, other users, lost devices, malicious extensions and compromised client code can observe or do. Client encryption should keep private payloads out of the sync storage/backend plaintext path, but it does not defeat malicious JavaScript served to an unlocked browser or all traffic-analysis metadata. **ENC-02 — Use random keys and authenticated encryption.** Generate cryptographically secure random vault key material on-device. Bind record/account-vault context, logical domain, object identity, schema and key epoch as authenticated associated data where appropriate to prevent substitution. Do not put Goal notes, Habit history, food diary, body measurements, quantities or allocations into public chain data or public provider state. Domain names or counts exposed as metadata must be minimized and documented.

**ENC-04 — Provide a real key-wrapping and recovery mechanism.** Wrap random vault keys under independent client-held unlock/recovery material rather than re-encrypting data with a predictable identifier. Use a maintained password-KDF implementation and a justified parameter policy where a vault passphrase is offered; benchmark supported devices without silently weakening security to make a demo fast. A high-entropy recovery secret must be generated and handled locally. Never upload it unencrypted, include it in analytics, display it in captured evidence or put it into URLs/browser history. Explain recovery responsibilities during setup.

**ENC-05 — Preserve keys safely across device sessions.** Decide whether a trusted device persists wrapped key material or a platform-supported nonextractable key; document the exact browser behavior and its limits. Do not store an unwrapped vault secret casually in localStorage or a service worker cache. Keep unlocked material scoped to the active account/session, clear it on lock/sign-out as appropriate and fence in-flight operations. “Remember this device” is an explicit user choice with a clear local-security implication, not an assertion of hardware protection the browser does not provide.

**ENC-06 — New-device onboarding must preserve the existing vault.** After authentication, fetch the authenticated vault manifest, then unlock and validate before importing. Present recovery choices and leave existing ciphertext untouched. A new device can explicitly create a separate fresh vault only after understanding that it is not recovering the old data. **ENC-07 — Support revocation and key epochs honestly.** Device/session revocation must immediately prevent future authorized server access and reject outstanding stale-session writes. Do not claim full cryptographic revocation if only an access token was deleted. Keep the implementation scope and remaining rotation limitations explicit.

**ENC-08 — Keep account recovery distinct from data recovery.** Losing email access, forgetting an auth password and losing vault unlock material are different failure modes. Invalid credentials or corrupted input must preserve current data. Plain exports, where intentionally supported, need explicit disclosure that the contents are readable and private; do not make public logs or support uploads of them automatic.

**ENC-10 — Verify plaintext does not escape.** Use clearly fictional sensitive markers in integration fixtures, then inspect actual outgoing sync payloads, stored records, backend logs, browser caches and generated build artifacts. **SYN-06 — Preserve append-only evidence and corrections.** Contributions, reversals, immutable plan revisions and relevant audit events retain their original IDs and relationships across sync. **SYN-07 — Prevent deletion resurrection.** Maintain tombstones and epoch/compaction policies that account for offline devices. Server deletion and account reset require clear propagation and retention behavior. Test an old client reconnecting after deletion, compaction and schema upgrades.

**SYN-08 — Support offline use without pretending everything is synchronized.** Local records and already available private data remain useful offline. Expired authentication pauses remote delivery while preserving local work; unlock and sign-in can resume it. A public provider outage should not stop a user logging water or a Habit. **SYN-09 — Fence account switching and late results.** Every async private request and queued operation captures the account/vault/session generation that created it. If using per-vault serialization, keep public market budgeting separate from private account coordination and do not create a single global private-data bottleneck.

**SYN-12 — Keep sync efficient and bounded.** Use incremental pages, change cursors or equivalent bounded deltas, sensible batching and debounced writes. Avoid constant background polling while the app is hidden. Document an initial practical sync target, such as updates becoming visible within several seconds on a healthy active connection, and measure it rather than claiming real time automatically. Add retry caps, backpressure, per-vault storage limits and safe failure messages; limits must not discard accepted private records silently.

**SYN-13 — Handle schema and protocol upgrades.** Reject unsupported future versions safely. Old clients that cannot preserve new fields must not write destructive down-conversions. Coordinate domain migrations and sync epochs so a service-worker-cached old UI cannot erase new plan revisions or widget configuration. Test the mixed-version window and document code/data rollback compatibility rather than assuming a previous Worker can read new ciphertext payload schemas.

**SYN-14 — Keep sync observability private.** Operational logs may include bounded sanitized status, timings, byte/count buckets and opaque server request IDs where needed, not decrypted records, email codes, auth tokens, wallet challenges or raw private IDs unnecessarily.
