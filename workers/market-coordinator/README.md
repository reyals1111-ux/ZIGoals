# Isolated durable public-data coordinator
The current Run11 path uses trusted `ZIGOALS_MARKET_QUOTES_MODE=durable-v1` and the app's `MARKET_QUOTES` binding to named `QuoteService`. Default public HTTP returns404. Missing/failed binding or invalid policy returns degraded/setup-required evidence and never falls back to the legacy process-local provider. Existing protected Alpha config remains unchanged.
Quotes, canonical catalog, history, insights, supported token and RWA reads share the account authority. Each actual provider HTTP request requires durable reservation, ownership and DISPATCHED accounting before I/O; settlement/publication obey work and generation fences. Public cache persists separately from attempts. Missing endpoint cost/entitlement fails closed. Pair-specific failed ZIG evidence does not poison valid Bitcoin evidence.
Queues, accepted interactive reservations, bounded followers, endpoint priority aging, account/endpoint/pair breakers, Retry-After gates and paid half-open probes are bounded. Waiting work does not occupy dispatch concurrency. Cache hits do not spend credits. Dispatched failures/uncertainty remain conservatively charged; cancellation cannot refund an already dispatched request. Retention compacts attempts into cumulative accounting and keeps replay tombstones within the supported horizon; old attempts never recreate/refund a charge.
Quote callers use a random cancellation capability and `/api/market-quotes/cancel` to remove their follower promptly on abort/navigation without canceling another caller's owner. Browser keepalive delivery cannot be guaranteed after abrupt process kill or network loss; those followers expire under bounded deadlines. Native Request.signal cancellation alone was not propagated through local Miniflare and is not claimed as sufficient. Nonquote follower cleanup uses its bounded request deadline.
Configuration: opaque server-selected `MARKET_ACCOUNT_ID`, `MARKET_QUOTE_DISPATCH=durable-v1`, strict `MARKET_POLICY` and coordinator-only `COINGECKO_DEMO_API_KEY`. Confirm account limits, current usage, reset timezone and every enabled endpoint cost before activation. Confirmed UTC calendar or an exact supplied month window is required. Fixture clock flags never belong in activated configs. Names/SQLite migrations/service bindings are in the actual local templates; all remain nonpublic and unconfigured.
Local evidence: `scripts/run11/market-crash-matrix.test.mjs`, `market-fanout.test.mjs`, `market-disconnect.test.mjs`, `market-browser.test.mjs`, `market-open-next.test.mjs`, `packaged-runtime.test.mjs`, plus Run10 durable boundary tests and server policy suites. All provider calls are intercepted fixtures. No test result here proves live provider entitlement, account costs, hosted activation or physical-device behavior. Current source-bound counts/receipts are in `docs/run11/PROOF.md`; owner handoff is `docs/run11/ACTIVATION.md`.
Do not restore the old process-local path as a silent failover or reset durable counters/tombstones to regain capacity. Preserve state, review current policy/source and recover forward. No transaction/signing capability is granted by this coordinator.

## Request cost and abuse limits (Session R1, Q-WRK-01/02)
Session Q found that one anonymous client could spend the account object's free daily allowance (100,000 requests and 100,000 rows written per day on Workers Free) through `/api/market-*`: one command per pair, a write on every command including cache hits, and 25–50 ms polling. Since Session R1:

- **Commands per request.** QuoteService sends one `acquire-many` per request: cache hits, leases, follower registrations and the first provider read's admission in one transaction. Each provider read then ends with one `complete`, which settles it, publishes what it verified and admits the next read (or the documented ZIG token fallback) in the same transaction. A read that waits for a slot polls `admit` at most every 250 ms (at most 8 times); followers poll `poll-many` at most every 250 ms (at most 4 times, the last at the deadline, so a publication just before it still wins). Nothing grows with the number of pairs. Measured with the in-process authority (`apps/web/lib/server/market-request-cost.test.ts`): a cold 64-pair insights request is 3 commands and 146 rows written (Session Q's reproduction: 138 commands and 753 rows); the same request cached is 1 command and no write.
- **Writes only on change.** Every command runs in a buffer and commits only a real change (a lease, an attempt transition, a publication, a follower registered or retired). Cache hits, waits, polls that only wait and refusals write no row.
- **At most 64 pairs.** `/api/market-insights` answers 400 above 64 pairs; QuoteService refuses more than 64 pairs without a command; the browser sends 32 pairs per request (`MARKET_REQUEST_CHUNK`).
- **Daily row budget.** The object counts the rows it writes per UTC day and refuses new cold work with `DAILY_LIMIT` once `MARKET_POLICY.dailyRowBudget` (default 20,000, a fifth of Workers Free; 1,000 to 10,000,000) is reached. Cached prices keep serving. On Workers Paid the owner may raise it.
- **Per-client shares**, all derived from the policy (`CLIENT_LIMIT`, reported as `LOCAL_BUDGET`): attempts per rolling minute ⌊operating.minute/4⌋, attempts waiting or in flight ⌊queueLimit/4⌋, works held ⌊maxWorks/2⌋, followers 32, credits per UTC day ⌊operating.monthly/31⌋ and new works per UTC day ⌊dailyRowBudget/16⌋. With the proposed profile and the default budget: 7, 4, 32, 32, 161 and 1,250. A request without a client (local runtimes only) is bound by every global limit and by no per-client one.
- **Isolate cache.** A QuoteService isolate answers a request whose works are all fresh in its memory (at most 8 MB of evidence, by the account's own freshness rule) with no command, and keeps the last complete catalog text until it is 24 hours old. It never answers a cold work. Both are off under the fixture clock. Isolate hits are not in the aggregate telemetry.

**Two apps, one budget (Session U Part 2e).** The app labels every coordinator request `x-market-caller` from its own bindings, never from its caller's request: `friends` when it has the `PRIVATE_SYNC` binding (the acceptance app), `public` otherwise (the public Alpha). QuoteService refuses any other value and treats an unlabelled request as public; the account object gets the label on its internal request. With `MARKET_POLICY.partition` (`{"publicPercent": 10..90}`), the public caller's commits are also counted in the day row's `publicRows`, and public new work stops at that share of `dailyRowBudget` (`DAILY_LIMIT`, shown as `LOCAL_BUDGET`) while the acceptance app keeps the rest. Without `partition` the label changes nothing: no field is written and every decision is the same (`market-partition.test.ts`, byte-identical storage). Tests: `market-partition.test.ts`, `scripts/run11/market-partition.test.mjs` (two apps in workerd), `market-route-coverage.test.ts`. **Public cold work (Part 2f):** all public callers together may start at most `MARKET_POLICY.publicColdWorks` new works per UTC day (default ⌊`dailyRowBudget`/8⌋), counted in the day row's `publicWorks`; a request that would exceed it is refused whole (`DAILY_LIMIT`) without a write. Cache hits and followers never count; `friends` is not capped by it (`market-cold-work.test.ts`).

**Client identity and privacy.** The app sets `x-market-client` only from Cloudflare's `cf-connecting-ip`: an IPv4 address, or an IPv6 address by its /48 (`apps/web/lib/server/market-client-address.ts`). It builds a new request to the binding, so a header the caller sent is never forwarded; loopback and unparsable values give no client. QuoteService accepts only that format. The account object stores neither the address nor the group: a client is one of 4,096 buckets, the first 12 bits of an HMAC-SHA256 of the group under a random key that is replaced every UTC day (`market-client-key`). Per-day rows (`market-day:<UTC date>`) hold the day's row count and each bucket's credits and new works; a committing command deletes up to 4 day rows older than the previous UTC day, so none outlives about 48 hours of activity. The bucket also marks the attempts and followers it holds: a follower ends within a second, and an attempt's receipt is deleted with its retry window (`retryRetentionMs`, one hour by default, at most 24 hours). Once the day's key is replaced, no stored bucket can be linked to an address group again. Nothing logs or returns a client value. A shared bucket only makes limits stricter.

**Existing rows.** Every v1 row is read in place: no migration, no deletion, no change to the class, binding or migration tag. New rows and fields are additive (`market-day:*`, `market-days`, `market-client-key`, a bucket on attempts and followers, evidence up to 16,000 characters stored inline in its work row). Rolling the coordinator back to v1 is safe once `dailyRowBudget` is removed from `MARKET_POLICY` (v1's strict schema would refuse it and deny all market work); v1 reads inline evidence and ignores the new rows.

**Rollout order** (owner, after merge):
1. Redeploy market-coordinator from the merged source.
2. Rebuild the acceptance app hermetically (`build:alpha` with no env file in the checkout) and redeploy it.
3. Re-attach the route.

In the mixed state (old app, new coordinator) every coordinator-side protection holds: one command per request phase, no writes on hits, 250 ms polling, the daily row budget and the 64-pair refusal. Per-client limits do not, because the old app sends no client; and the old app's insights requests of more than 64 pairs are refused (degraded) until the app is redeployed.

## Catalog validation, 404 cache and the history pool (Session S, FIX_PLAN C2)
Session R1 bounded what one client can spend. Session S also refuses work that can only waste the shared budget, before any lease or charge (`apps/web/lib/server/market-catalog-guard.ts`; tests in `market-catalog-guard.test.ts`).

- **Unknown asset IDs:**
  - When catalog evidence is published, the account also writes that partition's IDs as a compact index: a pointer row `market-catalog-ids:<kind>` plus chunks of whole IDs. The rows sit outside `work-index`, so evicting the catalog evidence never removes them.
  - A cold quote, insights or history work whose ID is not in an **authoritative** index is refused with `UNKNOWN_ASSET` (reported as `UNSUPPORTED`): no lease, no row, no credit, no provider call.
  - An index is authoritative with at least 1,000 coins or 10 RWAs, and when it is not under 90% of the index it replaced.
  - The app's featured markets (`FEATURED_MARKET_IDS` in `market-assets.ts`) are always accepted.
  - History IDs must also have the shape the provider path accepts (`[a-z0-9_-]+`).
  - Without an authoritative index, the account behaves as before, within Session R1's limits.
  - Catalog evidence published before Session S has no index. It is treated as cold once, so the first catalog request after the redeploy refetches it (two catalog credits) and writes the index.
- **Provider 404s:**
  - A history read that the provider answers with 404 is remembered for that coin for 15 minutes, in one row `market-not-found` of at most 128 entries.
  - Later history requests for the coin, any currency or range, are refused with `NOT_FOUND_RECENTLY` (`UNSUPPORTED`) and cost nothing. A repeated unknown coin therefore uses one provider read.
- **History's own share** (`historyLimits` in `market-budget-policy.ts`, derived from the policy, with no new field). History reservations carry `pool: "history"`, and history may hold at most:
  - a quarter of `queueLimit`;
  - half of `operating.minute` and half of `operating.monthly` (folded history credits are kept in `archived.historyCredits` through compaction);
  - every dispatch slot but one.

  A history read waiting for its slot is passed over in the dispatch order, so it never holds back a quote behind it. A refusal is `HISTORY_LIMIT` (reported as `LOCAL_BUDGET`) and writes nothing.

**Idle retention (Session S, FIX_PLAN C7):** commits prune client day rows, but an object that went quiet kept its last ones and the client key. `MarketAccount` now keeps an alarm armed (one `getAlarm` read per object instance). At most every 6 hours it deletes day rows older than yesterday and an earlier day's client key (`sweepClientRows` in `market-client-limits.ts`), and it re-arms only while some remain.

**Cancellation fences (Session S, Part 8a):** a `cancel-followers` command whose token is new writes a 30-second fence row, so anonymous traffic could once spend the day's row budget with random tokens. Now:
- `/api/market-quotes/cancel` sends the edge address group as `x-market-client`, built only from `cf-connecting-ip`. QuoteService checks that header before every path, `/cancel` included, and forwards it.
- Removing matching live followers and answering a replayed token are never refused.
- A new fence is refused with no write (`DAILY_LIMIT`, or `FOLLOWER_LIMIT`; the app answers 503) once the day's rows reach `dailyRowBudget`, or once the day's fences reach ⌊budget/64⌋ in all or an eighth of that for one client bucket (`cancelQuota` in `market-client-limits.ts`). With the default 20,000 rows: 312 a day, 39 per bucket.
- The counts are an additive `cancels` field in the day row, deleted with it.
- **Mixed state:** an app deployed before Session S sends cancels without a client. They still work and count only toward the day's total. Deploy the coordinator first, then the apps (ALPHA_PRICES_ROLLOUT.md, FINAL_ACCTEST_REDEPLOY.md).

Tests: `apps/web/lib/server/market-cancel-quota.test.ts` and `scripts/run11/market-cancel-client.test.mjs` (workerd, including spoofed headers).

**Existing rows** are still read in place. The new rows (`market-catalog-ids:*`, `market-not-found`) and fields (`pool`, `archived.historyCredits`, `notFound` on `complete`) are additive. Session R1's code ignores them, so rolling the coordinator back to R1 stays safe; it then simply stops refusing.

## Optional aggregate telemetry
`MARKET_POLICY.telemetry` is absent by default. Separate activation approval can add `{ "enabled": true, "build": "<verified source or bundle identity>", "retentionHours": 24 }`. The strict schema allows one to168 hourly buckets for the current build. Build changes clear the prior aggregate; disabled mode clears it on next valid access. Expired buckets are excluded and deleted on access, not guaranteed physically erased while the object is idle. Retention concerns diagnostics only and never prunes charge/replay authority.
Only the private Durable Object `inspect-metrics` command reads these counters; the public Worker still404s and named quote service has no diagnostic route. (Its `/status`, Session U, answers only when its own `MARKET_POLICY` period ends, read from the binding: no account command, no usage figure.) Access belongs to authorized operator tooling, not browser users. There is no console log, external sink or analytics activation. Fixed counters cover cache hits/misses/coalescing, admission reasons, work classes, reserved/dispatched attempts and configured credits, priority, sanitized outcome, queue-wait and dispatched-duration buckets. They contain no URLs, headers, bodies, tokens, request IDs, asset/pair lists, account IDs or private data. Duplicate settlement cannot increment outcomes again; denied dispatch never increments spend. Counter saturation is explicit. Automatically recovered unknown dispatches remain charge authority facts; aggregate telemetry is not a billing ledger.
The proposed unactivated profile is `docs/run11/MARKET_PROPOSED_PROFILE.json`. Its null prerequisites/costs are deliberate and cannot be accepted as a runtime policy. Confirm usage/remaining allowance before choosing a safe ceiling; never erase durable spend to fit the proposal.

Synthetic matrix: `scripts/run11/market-load-matrix.test.mjs` runs four local app Workers against one real account object,62 owner pairs,48 follower pairs and240 warm pair results, a deliberately split body stream, ZIG fallback, malformed RWA, outage and truncated JSON. It asserts six provider calls and25 configured synthetic credits. Sixteen accepted-reservation pressure tests cover both monitoring-first and interactive-first orders, queue overflow, aging and two held dispatch slots. Node harness RSS is recorded as harness evidence; it is not Worker isolate peak memory or commercial capacity certification. Hosted process-kill experiments and isolate memory profiling remain separate external gaps.

## Local transaction interruption matrix
`scripts/run11/market-transaction-faults.test.mjs` bundles a separate test-only `FaultAccount` storage wrapper around the unchanged production authority. It throws after actual SQLite transaction writes (reservation, ownership, dispatch charge, settlement budget, settlement receipt, publication) to prove atomic rollback, or after transaction commit to simulate acknowledgement loss. Twelve authority cases restart workerd against the same persisted storage and assert charges, replay, receipt consistency, successor fences and month rollover. Eight named-service dispatcher cases additionally assert physical synthetic-provider send counts and cached replay after publication acknowledgement loss; since Session R1 they interrupt the dispatcher's own commits: `acquire-many` (reserve, own and dispatch in one transaction), `admit` (an attempt that waited for a slot) and `complete` (settlement or publication, one transaction). The fixture aligns dispatcher/authority clocks; requests within each fixture are serial. No fault controls, diagnostic routes or clock override are added to the production bundle.
Every run emits source-bundle-bound evidence into a temporary `run11-market-fault-summary-*` directory; `completedCases` must equal20, and the test runner must pass separately. These are executable local transaction interruption simulations, not proof of hosted OS termination, provider-side receipt certainty, or commercial operating capacity. Conservative unknown dispatch charges are never refunded. Existing transition restart, expiry/pruning, backward-clock, fairness and load matrices remain complementary.

The mixed-load matrix fixes the logical Worker clock so its provider-release/48-registration barrier is not a race against a follower's production one-second deadline on a busy CI runner. All61 valid owner results,48 fresh follower results,240 warm results and exact6 calls/25 credits remain required. Latencies remain real harness elapsed times; the fixed-clock matrix does not certify production deadline success under load. `market-follower-deadline.test.mjs` separately executes the unmodified production clock: a held synthetic response outlives its follower, whose result is explicitly LOCAL_QUEUE, while the owner's dispatch/charge remains intact; publication then supplies a fresh cache hit without another send. A controlled1.3second barrier reproduced the former hosted failure as three expired follower responses, not unrelated ZIG-error contamination.
